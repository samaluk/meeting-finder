# Issue tracker guide

Until a remote repository and issue tracker are chosen, keep work notes as local tracked drafts under `docs/work/` when that directory is introduced. Do not create GitHub issues, assign labels, or imply that a remote project exists.

Each draft should name the user trigger, canonical domain terms, affected F requirement, proposed interface, acceptance example, and validation seam. Separate design questions from implementation tasks. Link to [SPEC.md](../../SPEC.md), [GLOSSARY.md](../../GLOSSARY.md), an ADR, or a current source file as appropriate.

Do not use an issue draft to authorize deferred P01–P04 work. Resolve open public-contract decisions before describing an interface as stable. A completed draft can be turned into a remote issue later without changing its domain language.
